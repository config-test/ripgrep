# GitHub Actions → CircleCI translation notes

`.circleci/config.yml` was generated by mirroring `.github/workflows/ci.yml`.
Every build/test/lint command in it is copied from that workflow or from the
scripts in `ci/`. This file records what did *not* translate 1:1.

## Not translated

| GHA item | Why / what to do |
| --- | --- |
| `schedule: cron '00 01 * * *'` | CircleCI's in-config `triggers:` syntax is deprecated, and adding it to a workflow stops that workflow from running on pushes. Recreate the nightly run as a **scheduled pipeline**: Project Settings → Triggers → Add Scheduled Trigger, `0 1 * * *` UTC on `master`. |
| `actions/checkout@v4` | Replaced by the built-in `checkout` step. Fetch depth / submodule options are not configured because the workflow doesn't use them. |
| `dtolnay/rust-toolchain@master` | Replaced by the `install_toolchain` command, which drives `rustup` directly. |
| `build: winaarch64-msvc` (`windows-11-arm`) | CircleCI has no Windows ARM64 executor. This matrix entry is dropped — there is no equivalent. |
| `permissions: contents: read` | No CircleCI equivalent; CircleCI tokens aren't scoped per-workflow this way. |
| `fail-fast: false` | CircleCI workflows already run matrix jobs independently; a failure does not cancel siblings. |
| `$RUNNER_TEMP`, `$GITHUB_PATH`, `$GITHUB_ENV` | Replaced by `$HOME/cross-download` and appends to `$BASH_ENV`. |
| `.github/workflows/release.yml` | Deliberately **not** translated. It creates GitHub releases, uploads assets, and does build-provenance attestation via `GITHUB_TOKEN` / OIDC. Porting it would mean inventing deploy steps and secrets. If you want it, it needs a `GITHUB_TOKEN` in a CircleCI context plus tag filters. |

## Other deviations

- **`store_test_results` is not used.** `cargo test` emits no JUnit XML, and
  adding `cargo-nextest` or `cargo2junit` would change the test commands away
  from what `ci.yml` actually runs. `store_artifacts` is used instead, for the
  `build.rs` stderr log (the thing the "Show build.rs stderr" step exists to
  surface) and for `target/doc` in the `docs` job.
- **Cross-compilation runs on a `machine` executor**, not Docker. `cross`
  needs a Docker daemon that shares a filesystem with the checkout, which
  `setup_remote_docker` does not provide.
- **Non-pinned toolchains build on the `cimg/rust:1.96` image** and install
  `stable`/`beta`/`nightly` over it with `rustup`. `cimg/rust` publishes
  version tags only; there is no `stable` tag.
- **`fuzz/` is treated as a separate project.** It declares its own
  `[workspace]` and has its own `Cargo.lock`, so it gets its own
  `working_directory` and cache key. The ten crates under `crates/` are
  members of the root workspace and share one `Cargo.lock`, so they are built
  and tested together via `--workspace`, exactly as `ci.yml` does.

## Pinned versions worth re-checking

- `cimg/rust:1.96` — matches `rust-version = "1.96"` in `Cargo.toml`.
- `ubuntu-2404:2024.11.1` — machine image.
- `macos.m1.medium.gen1` / `xcode: 16.2.0` — requires a plan with macOS support.
- `circleci/windows@5.0.0` — the only orb used.
- `CROSS_VERSION: v0.2.5` — same pin as `ci.yml`.
